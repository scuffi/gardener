# Actions-native task authoring V1

A Gardener task is a Markdown file at `.gardener/tasks/<directory>/TASK.md`. YAML frontmatter declares
portable requirements; the Markdown body supplies model instructions. GitHub permissions, runner
images, checkout behavior, environments, and reusable-workflow pins are generated by the selected
target adapter and never belong in task source.

```markdown
---
schema: gardener.task/v1
id: bug-intake
name: Bug intake
description: Helps issue authors provide actionable bug reports.
trigger:
  event: github.issue.opened
  labels-all:
    - gardener-bug
tools:
  - repository.list_files
  - repository.read_file
effects:
  - issue.comment.create
network:
  default: deny
  allow: []
  deny: []
limits:
  runtime-seconds: 300
  max-turns: 8
  max-tool-calls: 12
  input-tokens: 24000
  output-tokens: 4000
---
Inspect the issue and repository evidence, then propose one concise issue comment.
```

## Semantics

- `id` is an immutable logical identity and does not depend on the source directory.
- `trigger` / `triggers` are normalized repository event requirements, not Actions YAML fragments.
- `tools` and `effects` are required portable capabilities, not permission grants.
- `network` declares the task's egress posture honestly. See [Network](#network); for
  `github-actions/v1` the host lists must be empty.
- `limits` are immutable ceilings enforced by the runtime.
- The instruction body cannot grant tools, effects, network access, or GitHub permissions.

## Triggers

Declare one trigger with `trigger:` or several with `triggers:`. Each entry names an exact
`(event, action)` pair, so every declared trigger compiles to an exact provider filter. A task may
declare each trigger kind at most once.

| Trigger kinds | Extra keys |
| --- | --- |
| `github.issue.opened`, `.edited`, `.labeled`, `.unlabeled`, `.reopened` | `labels-all` |
| `github.issue_comment.created` | `labels-all` |
| `github.pull_request.opened`, `.reopened`, `.synchronize`, `.ready_for_review`, `.converted_to_draft`, `.edited`, `.labeled`, `.unlabeled` | `labels-all` |
| `github.pull_request_review.submitted` | `labels-all` |
| `github.pull_request_review_comment.created` | `labels-all` |
| `github.discussion.created`, `.edited`, `.answered`, `.unanswered`, `.labeled`, `.unlabeled` | `labels-all` |
| `github.discussion_comment.created` | `labels-all` |
| `github.push` | `branches` (at least one branch filter, required) |
| `github.schedule` | `cron` (five-field expression, required) |
| `github.workflow_dispatch` | none |

`labels-all` is an AND filter over the labels of the issue, pull request, or discussion that carries
the event. Supplying a key that an event does not support is a compilation error.

`pull_request_target` is deliberately not modeled and can never be generated.

```yaml
triggers:
  - event: github.issue.labeled
    labels-all:
      - gardener-bug
  - event: github.pull_request.synchronize
  - event: github.push
    branches: [main, 'release/*']
  - event: github.schedule
    cron: 0 3 * * 1
  - event: github.workflow_dispatch
```

### Fork pull requests are never executed

Pull-request events can carry a head revision owned by a fork. Gardener plans **same-repository pull
requests only**, and there is no opt-in.

This is enforced twice. The compiler injects a head-repository equality guard into the generated
workflow, so a fork pull request does not start a run. The runtime independently re-checks the head
repository id against the enrolled repository before planning begins, so editing the generated
workflow cannot widen this. A pull request whose fork has since been deleted also fails closed,
because its head repository can no longer be proven to be the enrolled one.

Tasks that declare `repository.exec` produce an explicit error naming the tool, since executing
fork-authored code is the case this rule exists to prevent.

`pull_request_target` is not a supported trigger and never will be: it runs against the base
repository's write-capable token.

## Network

> **`repository.exec` has unrestricted network access. It is demo-only and is not
> production-ready.**

Gardener does not sandbox the GitHub-hosted runner. Any task that declares `repository.exec` runs
task-controlled commands with the runner's ordinary egress, so it **can reach any host on the
internet and can exfiltrate your private source code**, along with anything else readable in the
checkout. Treat `repository.exec` as equivalent to giving the model's chosen commands a normal
developer machine on your network.

Because of that, `github-actions/v1` requires the declaration to match reality:

| Task | Required `network` |
| --- | --- |
| Declares `repository.exec` | `default: allow`, `allow: []`, `deny: []` |
| Does not declare `repository.exec` | `default: deny`, `allow: []`, `deny: []` |

```yaml
# A task that declares repository.exec must say so honestly.
network:
  default: allow
  allow: []
  deny: []
```

**Host rules are rejected, not ignored.** A non-empty `allow` or `deny` list fails the build. This
target has no mechanism to enforce per-host filtering, and a filter that silently does nothing is
more dangerous than no filter at all, because it invites authors to believe egress is contained
when it is not.

`gardener build` prints a warning for every task that declares `repository.exec`, so the exposure is
visible at the point the capability is introduced.

If you need genuinely restricted egress, do not use `repository.exec` in V1.

## Tools

| Tool | Meaning |
| --- | --- |
| `repository.list_files` | List checked-out repository paths. |
| `repository.read_file` | Read checked-out repository file bytes. |
| `repository.exec` | Run commands in the unprivileged planning checkout. |
| `provider.api.read` | Read-only provider API access (REST `GET`/`HEAD` and GraphQL queries). |

`repository.exec` never receives a write-capable provider token. `provider.api.read` is served by the
bridge process; the token is never placed in model context or in the execution environment.

## Effects

`effects` is the exact operation authority for the task. List exact operation kinds, family globs, or
both. Globs expand deterministically into the canonical operation order, and overlapping selectors
collapse without duplication.

| Family glob | Expands to |
| --- | --- |
| `issue.*` | label add/remove, comment create/update, close, reopen, assignee add/remove |
| `pull_request.*` | comment create/update, review submit, reviewer request/remove, update, open draft, merge |
| `git.*` | `branch.create`, `commit.create` |
| `discussion.*` | comment create/update, answer mark/unmark, close, reopen |
| `check.*` | `check.rerun` |
| `release.*` | create, update, publish, delete |

> **Family globs grant every current and future member of that family.** Four of them deserve
> specific attention, and all four are usually better written as exact kinds:
>
> - `git.*` is **repository write authority**. `branch.create` and `commit.create` let the task add
>   commits and branches through the Git Data API, which is how a coding task produces changes. It
>   compiles to `contents: write`. It does **not** grant force-push, branch deletion, tag or release
>   authority, or the ability to merge; V1 confines these writes to `gardener/*` branches.
> - `pull_request.*` includes `pull_request.merge`, which merges code, and `pull_request.update`,
>   which can take a pull request out of draft.
> - `release.*` includes `release.publish` and `release.delete`, which are externally visible and,
>   in the delete case, destructive.
> - `check.*` includes `check.rerun`, which re-requests an Actions-owned check run and compiles to
>   `checks: write`.
>
> V1 applies every task-declared effect automatically through the checkout-free exact-plan job.
> Human approval is not part of this release. Prefer the narrowest selector that expresses the
> task—for example `pull_request.comment.create` rather than `pull_request.*`—because declaring a
> kind grants Gardener authority to execute it without an approval pause.

```yaml
effects:
  - issue.comment.create
  - git.*
```

An empty `effects` list produces an inspection-only task with no apply write scopes.

### Automatic V1 effects

All 29 declared effect kinds use the same automatic path in V1. The generated caller grants a fixed
read-only permission union for planning plus only the write scopes implied by the task's declared
effects. The model-facing planning job downgrades that grant to read-only; the checkout-free apply
job receives the write grant and executes only the exact Worker-validated plan. Ordered receipts,
provider preconditions, stop-on-first-failure, and exact-prefix resume still apply.

Human-in-the-loop approval is intentionally deferred until after every trigger and effect path is
qualified end to end. Tasks granting merge, release, check-rerun, or other destructive authority
must therefore be treated as automatic production automation, not as approval-gated workflows.

## Limits

`runtime-seconds`, `max-turns`, `max-tool-calls`, `input-tokens`, and `output-tokens` are required.

Two optional effect-plan ceilings are also available:

| Key | Meaning |
| --- | --- |
| `max-effect-operations` | Maximum operations in one plan. |
| `max-effect-bytes` | Maximum total plan artifact size. |

Gardener imposes no operation-count ceiling of its own. When these keys are omitted, only the
transport ceiling below plus provider and runtime ceilings apply; when present, both planning and
application fail closed. Omitted keys never reach canonical bundle bytes, so adding the keys later
is the only thing that changes a hash.

### The transport ceiling always applies

Independently of `max-effect-bytes`, a plan must serialize to at most **4 MiB** of canonical JSON,
and so must its receipt. This is the one technical bound on the planning/apply handoff and it is
enforced unconditionally, because there is deliberately no operation-count cap standing in for it.
The figure is stated in decoded bytes on both sides of the boundary, so the base64 artifact limit is
its exact encoded expansion rather than a number that quietly means 3 MiB of payload.

Repository file contents are not part of this budget. A `commit.create` step that materializes a
change carries only per-path metadata in the plan; the bytes travel in a separate changes artifact,
which is why the capture manifest has no file-count or change-byte ceiling of its own.

### Protected paths are never writable by a captured change

A captured change may not write `.git/`, `.github/workflows/`, `.github/actions/`, or `.gardener/`.
A materialized `commit.create` lists no paths in its own payload, so the instance policy's path
rules have nothing to inspect at plan time; the manifest is the one place where the full path set is
known before anything is applied, and it is rejected there. Without this, a run could rewrite the
workflow or task definition that governs the next run.

## `github-actions/v1` support

> **Status: work in progress, not released.** The compiler accepts and validates every trigger,
> tool, and effect documented above, but accepting a declaration is not the same as executing it.
> The apply chain is not yet pinned, so declaring an effect does not yet mean Gardener will perform
> it end to end. Treat this page as the contract being built toward, and do not depend on it until
> the bridge, reusable workflow, and compiler are published as one pinned release.

The target derives exact permissions rather than granting a fixed superset:

- planning always gets `contents: read` and `id-token: write`; declaring `provider.api.read` adds the
  read scopes implied by the declared triggers and effects, and nothing else;
- apply gets the union of the write scopes required by the declared effects, plus `id-token: write`;
- the generated caller job grants the union of both, because GitHub requires a caller's permissions
  to cover the workflow it calls.

### The caller union is a ceiling, not a grant

The caller job's `permissions:` block is the union of the planning and apply scopes, but **a called
reusable workflow can only ever receive permissions the caller already holds**. GitHub intersects
the two, so the union in the caller does not widen what any individual job gets: planning still
runs with only planning scopes and apply with only apply scopes, each declared on its own job.

The practical consequence is that the union is what a reader of the generated workflow sees at the
top of the file, and it is the correct thing to review when judging a task's maximum authority.

### Network

`network` must match the rule in [Network](#network): `default: allow` with empty lists for tasks
declaring `repository.exec`, `default: deny` with empty lists otherwise. Non-empty host lists are
rejected because this target cannot enforce them.

### Known limitation: one cron per task

A task may declare at most one `github.schedule` trigger, because triggers are unique by kind. If
you need several schedules, declare separate tasks. Modelling multiple crons in one task is
deferred rather than approximated, so that each admitted run still matches exactly one declared
trigger and the runtime can verify the cron it was started with.

## Build and enrollment

`gardener build` parses and validates source, emits canonical `TaskBundleV1`, computes its SHA-256,
validates target support, and writes deterministic lock/workflow files. `gardener connect` stores the
canonical bundle and trusted source path in customer-owned D1 and enables that exact hash for the
numeric repository identity.

The runtime loads task bytes from D1 after GitHub OIDC authentication, recomputes the hash, executes
only enrolled tools, and hands exact effect artifacts to the checkout-free effects job.

### Plan and receipt shape changed: redeploy fresh

The effect plan and its receipt are now ordered multi-step documents. They replaced a shape that
could express exactly one `issue.comment.create`, and the new schemas cannot read a row written by
the old one. There is no migration and none is planned: the change predates release, so the cutover
is a fresh deploy with a fresh database rather than an upgrade. A runtime holding stored plans or
receipts in the previous shape must be redeployed, not upgraded in place.
